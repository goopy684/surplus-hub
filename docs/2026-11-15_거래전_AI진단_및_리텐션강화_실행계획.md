# 거래 전 AI 유동성 진단 & 3-Way 처분 라우팅 — 타당성 분석, 리텐션 기획, 실행계획

- 작성일: 2026-11-15
- 대상 기능: Pre-Transaction AI Triage (IR 2차 고도화 Slide 04~06)
- 범위: `surplus-hub-api-v3`(백엔드), `surplus-hub-react/packages/core`, `apps/web`, `apps/mobile`
- 이 문서의 단가·가중치·임계값은 모두 **초기 가정값**이다. 현장 CBT 데이터로 보정하기 전까지 사실로 인용하지 않는다.

## 0. 한 줄 정의

판매글을 쓰기 전에 사진 1~3장과 3초 입력(소재·상태·물량 칩 + 규격 텍스트)만으로 (1) 유동성 점수 0~100, (2) 폐기 vs 고철 vs 직거래 손익 비교, (3) A/B/C 처분 경로를 돌려주는 게이트다. 결과는 버려지지 않고 "내 창고 보관함"에 남아, 주변 수요가 생기면 재방문을 부르는 자산이 된다.

## Phase 1. 타당성 분석과 리스크 진단

### 1.1 이 기능이 없애는 마찰

| 관점 | 현재 마찰 | 진단 기능이 바꾸는 것 |
|---|---|---|
| 공급자(공장장·시공 소장) | 판매글 작성 부담. 팔릴지 모르는 물건에 10분을 쓰지 않는다 | 글 없이 사진과 칩 3개로 "팔릴 물건인지"부터 확인 |
| 공급자 | 시세만 보면 장부가 대비 실망해 포기(Anchoring) | 비교 기준을 장부가가 아니라 "버릴 때의 손실"로 옮김 |
| 공급자 | 안 팔리는 재고를 올려 두고 헛되이 대기 | B(매입 호가), C(중량 일괄 처분)라는 퇴로를 즉시 제시 |
| 구매자 | 악성 재고가 섞인 피드에서 탐색 비용 증가 | 메인 피드는 A 경로 매물만 노출, 고유동성 배지로 신호 제공 |
| 플랫폼 | 매물 수는 늘어도 체결률이 낮아 이탈 | 등록 전 단계에서 순도를 관리, 진단 자체가 방문 이유가 됨 |

핵심은 "등록"이 아니라 "진단"을 첫 행동으로 만드는 것이다. 등록은 팔 물건이 있을 때만 일어나지만, 진단은 창고에 물건이 있기만 하면 일어난다.

### 1.2 엣지 케이스와 대응

| 엣지 케이스 | 왜 문제인가 | 대응 (이번 구현 반영 여부) |
|---|---|---|
| 사진만으로 두께·강종 판별 불가 | SUS304와 316, 동판 두께는 외관으로 구분되지 않음 | 소재 칩과 규격 텍스트를 사진보다 우선한다. Vision은 칩이 비어 있을 때만 보조로 호출 (반영) |
| Cold-Start: 지역 데이터 부족 | 검색·체결 이력이 없으면 수요 점수가 0에 수렴해 모든 자재가 C로 떨어짐 | 품목별 사전 확률(prior)로 베이지안 수축. 근거 3건 미만이면 `coldStart=true`로 표시하고 화면에 "품목 기본값 기반 추정" 고지 (반영) |
| 중량 미입력 | 폐기비·고철값을 계산할 수 없음 | 물량 칩(손수레/파렛트/1톤 트럭)으로 3초 입력. 그래도 없으면 100kg 가정 + `weightEstimated=true` 고지 (반영) |
| 점수 조작 어뷰징 | 상태를 "상"으로 속여 A 경로·배지 획득 | 사용자 입력 등급과 Vision 등급이 모두 있으면 낮은 쪽 채택. 배지는 점수 기준이고, 신고·모더레이션은 기존 체계 사용 (반영) |
| AI 비용 어뷰징 | 반복 호출로 Vision 과금 유발 | 분당 10회 제한 + 사용자당 일 30회 상한 + 이미지 해시 캐시 (반영) |
| 비정상 입력 | 중량 100만 kg 같은 값은 금액이 DB 정수 범위를 넘김 | 중량 상한 50톤. 구리 상 등급 최대치도 정수 컬럼 안에 들어온다 (반영) |
| 수요 조작 | 검색을 반복해 특정 품목 수요를 부풀림 | 검색 로그를 (사용자 또는 좌표 격자) 단위로 중복 제거하는 것이 정석. 이번에는 미반영, 한계로 기록 |
| 가격 추정 근거 부족 | 유사 매물 3건 미만이면 중앙값이 무의미 | `priceBasis=category_default`로 구분해 "추정"임을 표시 (반영) |
| Path B/C 매물의 구매자 접점 | 메인 피드에서 빼면 아무도 못 봄 | `track=B|C` 필터로 별도 트랙 목록 제공. 입찰 테이블·수락 플로우는 이번 범위 밖, 호가 제안은 기존 채팅으로 받는다 (부분 반영) |
| 폐기물관리법 | 폐기물로 분류된 물건의 중개는 허가 영역 | 플랫폼은 "유가물 거래 중개"만 한다. C 경로는 처리 업체를 "안내"하는 수준에 머문다 (정책) |

### 1.3 초저비용 하이브리드 산출 설계

원칙은 "LLM은 사진을 읽는 데만, 점수는 규칙과 DB 통계로"다. 점수·가격·경로는 전부 결정론적 계산이어서 LLM이 죽어도 결과가 나온다.

Vision 호출 조건은 아래 세 가지를 모두 만족할 때뿐이다.

1. 사진이 있다.
2. 사용자가 소재 칩과 상태 등급을 둘 다 주지 않았다(하나라도 비었다).
3. Vision 자격 증명이 설정돼 있다.

호출하더라도 첫 번째 사진 1장만 보내고, 기존 `registration.analyze_material_image`(이미 압축된 JSON 프롬프트)를 그대로 재사용한다. 결과는 (이미지 URL + 규격 텍스트) 해시 키로 24시간 캐시한다. 분석 결과가 규격 텍스트에 따라 달라지므로 텍스트를 키에 넣었다.

Vision은 서버가 이미지 URL을 직접 내려받는다. 그래서 우리 업로드 스토리지 URL일 때만 호출한다. 외부 URL이나 내부망 주소가 들어오면 내려받지 않고 규칙 기반으로 진단한다(SSRF 방지).

수요 점수에는 pgvector를 쓰지 않는다. 점수는 보관함 재산정 때마다 다시 계산되는데, 그때마다 임베딩을 만들면 비용이 생기고 진단 시점과 재산정 시점의 근거가 달라져 점수가 이유 없이 움직인다. pgvector 이웃은 한 번만 계산하는 직거래 가격 비교군에만 쓴다.

| 단계 | 방식 | 외부 과금 |
|---|---|---|
| 소재·규격 파싱 | 정규식 + 소재 별칭 사전 | 0원 |
| 상태 등급 | 사용자 칩 우선, 없으면 Vision | 조건부 1회 |
| 수요 밀도 | `search_logs`, `materials` 쿼리 + 파이썬 haversine | 0원 |
| 직거래 가격 비교군 보강 | 진단 시 1회, Postgres에서만 pgvector 이웃의 가격을 중앙값 계산에 추가(실패 시 키워드만) | 임베딩 1회(로컬 bge-m3 기준 0원) |
| 점수·경로·손익 | 산식 | 0원 |
| 보관함 재산정 | 저장된 인자 + 수요만 재계산. 임베딩도 만들지 않는다 | 0원 |

비용 추정(가정): 월 진단 500건, 그중 칩 미입력으로 Vision이 필요한 비율 40%, IR 원고의 건당 5~10원을 적용하면 월 1,000~2,000원 수준이다. 일 30회 상한이 있어 계정 1개가 유발할 수 있는 최대치는 하루 300원이다. 실제 건당 단가는 운영 로그로 확인해야 한다.

### 1.4 유동성 점수 산식

```
cond   = 상 1.00 / 중 0.85 / 하 0.50 / 미상 0.75
spec   = 0.60 + 0.40 × clarity          (clarity = 규격 신호 수 / 3, 최대 1)
demand = 0.45 + 0.55 × d                (d = 수축된 수요 밀도 0~1)

reuse  = 100 × cond × spec × demand
bonus  = materialValue × 30 × (1 − reuse/100)
score  = round(min(100, reuse + bonus))
```

규격 신호는 (a) 품목 또는 소재 식별, (b) 치수 표기(50A, 12T, 100x100, 600각, SQ, mm 등), (c) KS 규격 번호 또는 라벨 텍스트 존재, (d) 수량(0.5점)이다. 수량 칸이 비어 있으면 메모의 "20개", "5박스"를 읽는다.

진단은 두 축으로 나눠 본다(2026-11-15 개정).

| 축 | 입력 | 결정하는 것 |
|---|---|---|
| 품목 — 무엇인가 | 6개 업종 카테고리(조명/문·창호/건축자재/전기/설비/기타). 칩 > Vision > 메모에서 추정 | 재사용 수요의 기본값(prior) |
| 소재 — 무엇으로 만들었나 | 15종 칩(선택). 메모에서도 자동 인식 | 고철 단가, 소재 가치 보너스 |

처음에는 소재 하나가 수요 기본값까지 정했다. 그 결과 소재 목록에 없는 완제품은 이력 없는 지역에서 최고 65점이어서, 미개봉 LED 평판등이나 KS 밸브가 직거래(A)에 가지 못하고 B로 빠졌다. 실행 서버에서 확인하고 축을 분리했다.

품목별 기본값은 설비 0.65, 조명 0.60, 전기 0.60, 건축자재 0.55, 문·창호 0.40, 기타 0.35다. 현장 검증 전 가정값이다.

수요 밀도 d는 다음과 같이 구한다.

```
searches = 반경 10km·최근 30일 검색 로그 중 품목 용어 일치 건수
           (좌표 있는 로그 1.0, 좌표 없는 로그 0.3 가중)
sold, active = 반경 내 최근 90일 유사 매물의 체결/판매중 건수
base = (sold + 5 × prior) / (sold + active + 5)       ← prior는 품목 기본값. 체결 이력으로 수축 (Cold-Start 보정)
d    = base + (1 − base) × 0.6 × min(1, searches/10)  ← 검색 수요는 올리는 쪽으로만
coldStart = searches + sold + active < 3
```

체결 이력은 수요를 양방향으로 움직인다. 팔린 게 많으면 올리고, 안 팔린 매물만 쌓여 있으면 내린다. 검색은 올리는 쪽으로만 반영한다. 처음 설계는 검색까지 같은 수축식에 넣었는데, 그러면 prior가 높은 구리·SUS는 검색이 쌓일수록 점수가 내려가 보관함 알림이 영영 나가지 않았다. 구현 검증 중 발견해 위 식으로 바꿨다.

품목 용어는 소재를 알면 소재 별칭만 쓴다. "파이프"·"미사용" 같은 일반 토큰을 섞으면 무관한 검색까지 수요로 잡히기 때문이다. 소재를 모르거나 비금속일 때는 제목·규격의 품목 단어(최대 5개)를 쓰되, 숫자로 시작하는 토큰(50A, 20개)과 상태·거래 표현(미개봉, 팝니다 등)은 뺀다.

원소재 가치 보너스는 재사용 점수가 낮을수록 크게 붙는다. 그래서 상태가 나쁜 구리·SUS는 30~69점(B)으로 올라가고, 상태가 나쁜 비규격 철재는 30점 미만(C)에 남는다.

| 예시 (지역 이력 없음) | 품목 | cond | spec | demand | reuse | bonus | score | 경로 |
|---|---|---|---|---|---|---|---|---|
| 304 스텐 파이프 50A, KS 라벨, 상 | 설비 | 1.00 | 1.00 | 0.81 | 81 | 4 | 85 | A |
| KS 볼밸브 50A 10개 미사용, 상 | 설비 | 1.00 | 0.93 | 0.81 | 75 | 0 | 76 | A |
| LED 평판등 640x640 미개봉 20개, 상 | 조명 | 1.00 | 0.93 | 0.78 | 73 | 0 | 73 | A |
| 600각 포세린 타일 5박스 미개봉, 상 | 건축자재 | 1.00 | 0.93 | 0.75 | 70 | 0 | 70 | A |
| 구리 자투리, 하, 규격 없음 | 기타 | 0.50 | 0.73 | 0.64 | 24 | 23 | 46 | B |
| 방화문 2짝, 중 | 문·창호 | 0.85 | 0.73 | 0.67 | 42 | 1 | 43 | B |
| 비규격 잡자재, 하 | 기타 | 0.50 | 0.60 | 0.64 | 19 | 1 | 20 | C |

실행 서버(Postgres)에 같은 입력을 넣어 확인한 값이다. 같은 SUS304 배관에 주변 검색이 10건 쌓이면 d가 0.65에서 0.86으로 올라 85점에서 94점이 된다. 타일은 70점으로 문턱에 걸려 있어, 수량이나 치수를 빼면 B로 내려간다. 품목 기본값을 보정해야 할 지점이다.

매칭 확률과 소진 기간은 점수의 단조 변환이다(`p7 = clamp(score×0.95 − coldStart 5, 3, 95)`). 체결 데이터가 쌓이면 실제 소진일 분포로 교체해야 하는 임시 휴리스틱이다.

### 1.5 폐기손실 비교 산식

```
혼합폐기물 처리  = −(100,000 + 250 × 중량kg)        기본 수거·운반비 + kg당 처리비
일반 고철 파쇄   = +(소재별 고철 단가 × 중량kg)
자투리 직거래   = +(유사 매물 가격 중앙값, 3건 이상일 때)
                 아니면 max(고철값 × 상태배수, 150,000 × 상태계수)
실질 순효익     = 직거래 대금 + 폐기비 회피액
```

1톤 비규격 자재(상 등급)를 넣으면 폐기 −350,000원, 고철 +20,000원, 직거래 +150,000원, 실질 +500,000원으로 IR 원고의 예시와 같은 구조가 나온다. 소재별 고철 단가표는 코드 상수(`MATERIALS`)이며 시세에 따라 갱신해야 한다.

## Phase 2. 방문율·사용률을 올리는 리텐션 설계

구조적 한계는 "팔 물건이 생길 때만 온다"는 것이다. 해법은 방문 이유를 '등록'에서 '내 창고 가치 확인'으로 바꾸는 것이다.

### 2.1 네 가지 축

| 축 | 메커니즘 | 노리는 지표 | 구현 |
|---|---|---|---|
| ① 3초 숨은 현금 스캐너 | 홈 최상단 배너 → 사진·칩 3개 → 손익 비교 카드 | Activation(첫 방문 기능 실행률) | 구현 |
| ② 내 창고 보관함 + 점수 상승 푸시 | 진단을 저장 → 주변 검색 발생 시 재산정 → 10점 이상 오르거나 70점(A)을 새로 넘으면 푸시·인앱 알림 | WAU, 푸시 재방문율 | 구현 |
| ③ 급구 품목 전광판 | 주변 검색 수요 TOP 5 + 이번 주 폐기비 절감액 | DAU(홈 체크인), 진단 시도율 | 구현 |
| ④ 1장 요약 감정 리포트 | 공유 링크(로그인 불필요) + 하단 "내 창고도 진단" CTA | 바이럴 계수, 신규 유입 | 구현 |

보관함 푸시는 사용자가 "수요 생기면 알림 받기"를 직접 눌러 요청한 알림이다. 그래서 광고(MARKETING)가 아니라 자재 알림 설정(`push_material`)을 따르는 `TRIAGE_DEMAND` 타입으로 보낸다. 같은 진단에는 24시간에 1회만 보낸다.

전광판은 design.md의 정직성 규칙을 따른다. 검색 로그가 없으면 품목을 지어내지 않고 위젯 자체를 렌더하지 않는다. "유동성 85점+" 문턱은 `minScore` 파라미터로 열어 두되 기본값은 0이다. 초기 지역에서 85점 문턱을 강제하면 전광판이 항상 비기 때문이다.

### 2.2 추가 그로스 아이디어 (백로그)

### 2.3 퍼널 지표

진단 테이블의 상태와 타임스탬프만으로 퍼널이 나온다. 별도 이벤트 수집기를 붙이지 않는다.

| 단계 | 정의 | 산출 근거 |
|---|---|---|
| 진단 시도 | 기간 내 생성된 진단 수 | `created_at` |
| 진단 시도율 | 진단한 사용자 수 / 활성 사용자 수 | `user_daily_activity`와 조인(대시보드) |
| 보관함 저장률 | `vault_saved_at` 있는 진단 / 전체 진단 | `vault_saved_at` |
| 매물 전환율 | `listed_at` 있는 진단 / 전체 진단, 경로별 A/B/C 비율 | `listed_at`, `disposition_path` |
| 푸시 발송 | `notified_at` 있는 진단 수 | `notified_at` |
| 푸시 재방문율 | 알림 뒤 진단을 다시 연 건수 / 발송 건수 | `reopened_at` |

`GET /api/v1/ai/triage/funnel?days=30`(관리자)이 위 수치를 돌려준다. 가드레일 지표로 A 경로 매물의 30일 체결률을 본다. 점수가 높은데 안 팔리면 산식이 틀린 것이다.

`POST /ai/triage/{id}/convert` 요청은 `{ "price": 150000, "title": "...", "description": "...", "path": "A" }`이고 모두 선택이다. 생략하면 A는 직거래 추정가, B/C는 고철 추정가를 가격으로 쓴다. 응답은 `{ "diagnosis": {...}, "materialId": 34 }`다.

`path`는 판매자의 경로 재지정이다(IR 원고의 "판매자가 재지정할 수 있습니다"). AI가 C로 판정해도 판매자가 A를 고르면 메인 마켓에 올라간다. 다만 고유동성 배지는 경로가 아니라 점수(70점 이상)로만 붙으므로 재지정으로 배지를 얻을 수는 없다. 진단 행의 `disposition_path`는 AI 판정 그대로 두고 매물 행에만 재지정 값을 쓴다. 두 값의 차이가 곧 판정 불일치율 지표다.

```json

  "items": [
```

좌표가 없으면 `scope`가 `all`이 되고 전 지역 기준으로 집계한다. 정렬은 검색 수요(가중 건수) 순이다. 소재 사전에 없는 품목은 남이 입력한 검색어가 그대로 라벨이 되므로, 같은 검색어가 3회 이상일 때만 올린다. 한두 번 입력한 문구를 모든 사용자의 홈에 띄우는 것을 막기 위해서다.

수요 상승 알림 트리거: 검색이 기록될 때 백그라운드 태스크로 `rescore_vault_for_search(query, lat, lng)`를 건다. 기록되는 검색은 AI 검색(`GET /ai/search`)과 일반 키워드 검색(`GET /materials?keyword=`의 첫 페이지) 둘 다다. 홈과 검색 화면의 기본 검색이 후자라, 이를 빼면 실제 검색 대부분이 수요로 잡히지 않는다. `/materials`는 `lat`·`lng`를 받아 기록에만 쓰고 목록은 거르지 않는다. 태스크는 요청과 같은 DB 엔진으로 자체 세션을 연다. 검색어와 품목 용어가 맞는 `VAULT_SAVED` 진단만 재산정하고, 마지막 알림 점수보다 10점 이상 올랐거나 70점을 새로 넘었고, 24시간 내 알림이 없을 때 `notify(type="TRIAGE_DEMAND", reference_type="triage")`를 호출한다. 시세 상승 트리거는 고철 단가표가 아직 코드 상수라서 이번 범위에서 뺐다.

피드 순도: `crud_material`의 목록 조회와 `search._base_filter`가 `disposition_path`가 B/C인 매물을 기본 제외한다. `GET /materials?track=B|C`로만 조회된다. 판매자 본인의 판매 내역에는 그대로 보인다.

검증 시나리오

1. Path A: SUS304·상·규격 명확 → 70점 이상, 전환 시 메인 피드 노출, `liquidityScore` 반영.
2. Path B: 구리·하·규격 없음 → 30~69점, 전환 매물은 메인 피드에서 빠지고 `track=B`에서만 조회.
3. Path C: 비규격 철재·하 → 30점 미만, `track=C`.
4. Cold-Start: 검색·매물 이력 0건 → `coldStart=true`, 점수는 prior 기반으로 산출(0점으로 무너지지 않음).
5. LLM 장애: Vision 예외 → `analysisMode=rule_based`로 정상 응답.
6. 보관함 → 전환: 저장 후 목록 조회, 전환, 재전환 409.
7. 수요 상승: 보관함 저장 뒤 주변 검색 로그 누적 → 재산정 점수 상승 + `TRIAGE_DEMAND` 알림 1건, 24시간 내 중복 없음.
8. 전광판: 검색 로그가 있으면 TOP 목록, 없으면 빈 목록.
9. 권한: 남의 진단 조회·저장·전환 404, 비로그인 진단 401, 공유 토큰은 비로그인 조회 가능하되 주소·좌표 미포함.

### 3.5 알려진 한계

- 입찰(호가) 테이블과 원클릭 수락 플로우는 없다. B/C 트랙은 별도 목록 + 채팅으로 운영한다.
- 고철 단가·폐기 단가는 코드 상수다. 관리자 갱신 화면과 시세 상승 알림은 다음 단계다.
- 매칭 확률·소진 기간은 점수의 단조 변환이며 실측 보정 전이다.
- pgvector 유사도 보강은 Postgres에서만 동작하고, SQLite 테스트는 키워드 경로만 검증한다.
- 선반·명세서 일괄 스캔(Slide 05 모드 B)은 이 문서 범위 밖이다.
- 소재 15종의 고철 단가와 품목 6종의 수요 기본값은 모두 가정값이다. 구리 등급(A동·상동·파동)과 전선의 구리 회수율은 구분하지 않는다.
- 모바일 홈 검색은 위치 없이 기록된다(가중 0.3). 웹은 위치 권한이 이미 허용된 경우에만 좌표를 싣는다.
- 이미 A인 고점수 품목(예: 85점)은 검색이 쌓여도 알림이 가지 않는다. 최대 상승폭이 10점 미만이고 넘을 문턱도 없기 때문이다.
- 일 30회 상한은 조회 후 생성 방식이라 동시 요청이면 1~2건 넘을 수 있다. 분당 10회 제한이 상한선 역할을 한다.
- 로그아웃 시 React Query 캐시를 비우지 않는 것은 앱 전체의 기존 동작이다. 같은 기기에서 계정을 바꾸면 이전 계정의 보관함이 재조회 전까지 잠깐 보일 수 있다. 이번 범위에서 고치지 않았다.
- 기존 `/ai/analyze-image`는 여전히 임의 이미지 URL을 서버가 내려받는다. 진단 경로에만 스토리지 URL 제한을 넣었다.
